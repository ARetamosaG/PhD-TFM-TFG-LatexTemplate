\chapter{Diseño e implementación}
\label{cha:design}

Este capítulo aborda el diseño e implementación de las técnicas metaheurísticas descritas para la resolución del Problema
del Viajante. El objetivo es trasladar los conceptos estudiados a implementaciones funcionales que permitan comparar el 
comportamiento de los diferentes algoritmos bajo unas condiciones comunes.

\section{TSPLIB}
\label{sec:tsplib}

Para evaluar el comportamiento de los algoritmos es necesario disponer de un conjunto de instancias de referencia, que permita
realizar experimentos reproducibles y comparar los resultados obtenidos con otros trabajos. Para este propósito, se ha utilizado
\textbf{TSPLIB}, una colección de instancias de problemas de optimización combinatoria ampliamente utilizada en el estudio del 
Problema del Viajante, así como otros problemas relacionados \cite{tsplib}. Fue publicada en 1991, por el alemán Gerhard Reinelt
\cite{reinelt1991} \cite{wikipedia2026}.

La colección de instancias para el Problema del Viajante es accesible en \cite{tsp_dataset}. En ella se encuentra una lista de 
instancias estandarizadas ordenadas por orden alfabético. El nombre para las instancias consta de una palabra y un número:
\begin{itemize}
  \item La \textbf{palabra} representa, habitualmente, la inicial del autor que diseñó el problema, un acrónimo de la 
  procedencia de los datos o el tipo de problema real del que se extrajo.
  \item El \textbf{número} indica el total de nodos o ciudades que componen la instancia.
\end{itemize}
Por ejemplo, en el caso de la instancia \texttt{berlin52}, se tiene que dicha instancia cuenta con 52 ubicaciones reales de la 
ciudad de Berlín.

Si se descarga una de estas instancias, por ejemplo \texttt{berlin52}, se obtiene un fichero \texttt{.gz}, que al descomprimirse,
se obtiene el fichero en su formato \texttt{.tsp}. Este tipo de ficheros se puede abrir con cualquier editor de texto, ya sea el 
bloc de notas o un entorno de desarrollo cualquiera.

El fichero \texttt{berlin52.tsp} presenta el siguiente aspecto:

  \label{fig:inst_info}
\end{figure}

Como se puede observar, cada instancia cuenta con los siguientes campos:
\begin{itemize}
  \item \textbf{NAME}: indica el nombre de la instancia, idéntico al del fichero.
  \item \textbf{TYPE}: el tipo de problema de optimización al que se corresponde la instancia. En todos los casos de este 
  trabajo será TSP.
  \item \textbf{COMMENT}: incluye una pequeña frase opcional informando sobre la instancia. En este caso, nos confirma que las
  52 localizaciones de la instancia pertenecen a la capital alemana.
  \item \textbf{DIMENSION}: incluye la dimensión de la instancia, esto es, el número de nodos.
  \item \textbf{EDGE\_WEIGHT\_TYPE}: indica cómo se determinan las distancias. En este caso, los nodos se presentan como \textbf{
  coordenadas en un plano euclideano de dos dimensiones} (\texttt{EUC\_2D}). Otros valores posibles son \texttt{EXPLICIT} o 
  \texttt{GEO}, entre otros.
  \item \textbf{NODE\_COORD\_SECTION}: es la información más importante de la instancia, puesto que se trata de las \textbf{
  coordenadas de cada una de las localizaciones}. En otras instancias, se incluyen los \textbf{pesos de las aristas} en su lugar.
\end{itemize}

Además de esta colección de instancias estandarizadas, TSPLIB también cuenta con una sección con los \textbf{resultados óptimos}
para cada una de estas instancias. Se puede consultar en \cite{tsp_best}. La existencia de esta sección es crucial, puesto que 
el conocimiento de la solución óptima es clave para calcular la proximidad de los óptimos propuestos por los algoritmos con el 
óptimo global, y así establecer unas métricas de eficiencia.

\subsection{Cálculo del coste de una ruta}
\label{subsec:route_cost_calc}

Una vez conocido el entorno de Python y la librería \textbf{tsplib95}, el próximo paso es desarrollar una pequeña función
que nos permita calcular el coste de una ruta. Una sencilla implementación podría ser la siguiente:
\newline
\begin{lstlisting}[style=PythonStyle]
def route_distance(route, problem):

  # Inicializar la distancia total:
  distance = 0

  # Iterar sobre cada nodo de la ruta:
  for i in range(len(route) - 1):

      # Añadir la distancia entre el nodo actual y el próximo:
      distance += problem.get_weight(route[i], route[i+1])

  # Sumar la distancia del último nodo al origen:
  distance += problem.get_weight(route[-1], route[0])

  # Devolver el valor de la distancia total:
  return distance
\end{lstlisting}

Con esta función, si se le introduce un problema cualquiera, y una ruta que corresponda a dicho problema, se obtiene la 
distancia total de esa ruta:

\begin{verbatim}
  >>> route = list(problem.get_nodes())
  >>> print(route_distance(route, problem))
  22205
\end{verbatim}

Se obtiene que, para una ruta en orden ascendente (desde el nodo 1 hasta el nodo 52), el coste de la ruta es $22205$.

\section{Implementación de metaheurísticas}
\label{sec:metah_imp}

Una vez visto el lenguaje de programación, la colección de instancias estandarizadas, la librería de Python adaptada, y

\subsection{Algoritmos genéticos}
\label{subsec:ga_imp}

Para realizar la implementación de los algoritmos genéticos, se va a replicar el mismo esquema teórico descrito en la 
sección~\ref{sec:ga}.

Para inicializar la población, se baraja la lista de nodos, y se seleccionan tantos individuos como determine el parámetro
del tamaño de población:
\newline
\begin{lstlisting}[style=PythonStyle]
import random

def create_individual(nodes):

  # Copiar la lista de nodos:
  individual = nodes.copy()

  # Mezclar la lista de nodos:
  random.shuffle(individual)

  # Devolver la lista aleatoria:
  return individual

def initialise_population(nodes, population_size):

  # Inicializar la lista de la población:
  population = []

  # Iterar según el tamaño establecido para la población:
  for _ in range(population_size):

      # Añadir un individuo (lista aleatoria de nodos):
      population.append(create_individual(nodes))

  # Devolver la población:
  return population
\end{lstlisting}

Por ejemplo, para una pequeña población de prueba con cinco individuos, se obtiene:

\begin{verbatim}
  >>> nodes = list(problem.get_nodes())
  >>> pop = initialise_population(nodes, 5)
  >>> for ind in pop:
  >>>   print(ind)

  [47, 18, 2, 21, 42, 14, 31, ..., 39, 11, 6, 12, 13, 52, 19]
  [4, 11, 13, 28, 25, 7, 35, ..., 39, 38, 6, 27, 20, 18, 9]
  [41, 23, 11, 45, 50, 40, 3, ..., 29, 47, 38, 43, 7, 25, 13]
  [48, 29, 17, 38, 7, 51, 37, 1, ..., 8, 45, 34, 31, 50, 24, 13]
\end{verbatim}

Para evaluar la población, se hace uso de la función \texttt{route\_distance()} descrita en la 
sección~\ref{subsec:route_cost_calc}, y se calcula su inversa para obtener la \textit{fitness}:
\newline
\begin{lstlisting}[style=PythonStyle]
def fitness(route, problem):
  return 1.0 / route_distance(route, problem)
\end{lstlisting}

La ruta ordenada de \texttt{berlin52} da la siguiente \textit{fitness}:

\begin{verbatim}
  >>> nodes = list(problem.get_nodes())
  >>> print(fitness(nodes, problem))
  4.503490204908804e-05
\end{verbatim}

El resultado es un número extremadamente bajo, indicando el ínfimo valor de \textit{fitness} que presenta esta ruta.

El operador de selección a implementar es \textbf{torneo}. Se seleccionan $k$ individuos aleatorios, y se determina el 
ganador según su \textit{fitness}:
\newline
\begin{lstlisting}[style=PythonStyle]
def tournament_selection(population, problem, k):

  # Se seleccionan k individuos al azar:
  tournament = random.sample(population, k)

  # El ganador es el que tiene mayor fitness (menor distancia):
  winner = max(tournament, key=lambda ind: fitness(ind, problem))

  # Devolver el individuo ganador:
  return winner
\end{lstlisting}

Se puede continuar la ejecución de prueba empleando unos parámetros al azar. Si se escoge una pequeña población de cinco
individuos nuevamente, y se realiza un torneo con $k=2$:

\begin{verbatim}
  >>> nodes = list(problem.get_nodes())      
  >>> population = initialise_population(nodes, 5)
  >>> print(tournament_selection(population, problem, 2))
  [5, 24, 40, 14, 11, 44, 17, ..., 31, 4, 21, 29, 45, 8, 10]
\end{verbatim}

Se obtiene el individuo ganador.

El operador de cruce a implementar es \textbf{\textit{Order Crossover}}. Se copia un segmento del primer progenitor y se 
rellena el resto con nodos del segundo progenitor respetando su orden, y viceversa. En este caso, se requiere de una función
auxiliar interna, \texttt{fill\_child()}, encargada de realizar el proceso de relleno del descendiente:
\newline
\begin{lstlisting}[style=PythonStyle]
def ox_crossover(parent1, parent2):

  # Determinar la longitud del progenitor:
  size = len(parent1)

  # Inicializar los descendientes como 'listas vacías':
  child1, child2 = [-1]*size, [-1]*size
  
  # Seleccionar y ordenar dos puntos de corte aleatorios:
  point1, point2 = sorted(random.sample(range(size), 2))

  # Copiar el segmento intermedio del progenitor1 al descendiente1:
  child1[point1:point2+1] = parent1[point1:point2+1]

  # Lo mismo para progenitor2 y descendiente2:
  child2[point1:point2+1] = parent2[point1:point2+1]
  
  # Función auxiliar interna para rellenar el resto:
  def fill_child(child, alt_parent):

      # Inicializar el puntero de escritura después del segundo punto de corte: 
      child_pointer = (point2 + 1) % size

      # Iterar por cada nodo en el progenitor alternativo:
      for node in alt_parent:

          # Comprobar que la ciudad no esté presente ya en la copia del segmento
          # inicial:
          if node not in child:

              # Si no está, se inserta en la posición actual:
              child[child_pointer] = node

              # Avanzar el puntero a la siguiente posición, volviendo a 0 si se
              # supera la longitud máxima:
              child_pointer = (child_pointer + 1) % size

      # Devolver el descendiente relleno:
      return child

  # Extraer y reordenar el progenitor2 desde el siguiente nodo después del segundo 
  # corte:
  parent2_ordered = parent2[point2+1:] + parent2[:point2+1]

  # Lo mismo para el progenitor1:
  parent1_ordered = parent1[point2+1:] + parent1[:point2+1]

  # Rellenar descendiente1 con progenitor2 reordenado:
  child1 = fill_child(child1, parent2_ordered)

  # Rellenar descendiente2 con progenitor1 reordenado:
  child2 = fill_child(child2, parent1_ordered)

  # Devolver los descendientes:
  return child1, child2
\end{lstlisting}

El operador de mutación a implementar es \textbf{\textit{Inversion Mutation}}. Se seleccionan dos puntos aleatorios,
y se invierte el segmento comprendido entre dichos puntos:
\newline
\begin{lstlisting}[style=PythonStyle]
def inversion_mutation(individual, mutation_prob):

  # Si se supera el umbral de mutación:
  if random.random() < mutation_prob:

      # Determinar la longitud del individuo:
      size = len(individual)

      # Seleccionar y ordenar dos puntos de corte aleatorios:
      point1, point2 = sorted(random.sample(range(size), 2))

      # Invertir el segmento:
      individual[point1:point2+1] = reversed(individual[point1:point2+1])

  # Devolver el individuo:
  return individual
\end{lstlisting}

Un valor realista de probabilidad de mutación, por ejemplo $10\%$, tomaría varios intentos para mostrar resultados. Se
puede fijar este valor a 1, para que \texttt{random.random()} siempre devuelva un número inferior y ver el comportamiento

def genetic_algorithm(
  distance_matrix,
  pop_size,
  num_generations,
  k,
  crossover_prob,
  mutation_prob,
  num_elites,
  patience):
    
  # Obtener la lista de nodos del problema:

  # Generar la población inicial:
  population = initialise_population(nodes, pop_size)

  # Inicializar la variable para la mejor ruta encontrada:
  best_global_solution = None

  # Inicializar la mejor distancia (infinito para garantizar su actualización):
  best_global_distance = float('inf')

  # Iterar por cada generación:
  for generation in range(num_generations):

    # Ordenar la población actual de mayor a menor fitness:
    population.sort(
        key=lambda ind: fitness(ind, problem), reverse=True
    )

    # Calcular la distancia del mejor individuo de la generación actual:
    current_distance = route_distance(population[0], problem)

    # Si el mejor individuo de la iteración mejora la solución global:
    if current_distance < best_global_distance:

      # Actualizar la global:
      best_global_distance = current_distance

      # Guardar una copia de la solución:
      best_global_solution = population[0].copy()

    # Inicializar la lista para la siguiente generación de soluciones:
    new_population = []

    # Aplicar elitismo al preservar los 'num_elites' mejores individuos de la 
    # generación anterior:
    for i in range(num_elites):
      new_population.append(population[i].copy())

    # Aplicar reemplazo generacional hasta completar el tamaño de la población:
    while len(new_population) < pop_size:

      # Seleccionar dos progenitores mediante torneo:
      parent1 = tournament_selection(population, problem, k)
      parent2 = tournament_selection(population, problem, k)

      # Evaluar probabilidad de cruce y ejecutar si procede:
      if random.random() < crossover_prob:
        child1, child2 = ox_crossover(parent1, parent2)

      # Si no se aplica cruce:
      else:

        # Los descendientes se copian:
        child1, child2 = parent1.copy(), parent2.copy()

      # Aplicar el operador de mutación a cada descendiente:
      child1 = inversion_mutation(child1, mutation_prob)
      child2 = inversion_mutation(child2, mutation_prob)

      # Insertar el primer descendiente en la nueva población:
      new_population.append(child1)

      # Si la población no está completa:
      if len(new_population) < pop_size:

        # Añadir el segundo descendiente:
        new_population.append(child2)

    # Sustituir la población antigua por la nueva:
    population = new_population

    # Se imprime la métrica de convergencia alcanzada en la iteración actual:
    print(
      f"Generación {generation + 1} | 
      Mejor distancia: {best_global_distance:.2f}"
    )

  # Devolver la mejor ruta y su distancia:
  return best_global_solution, best_global_distance
\end{lstlisting}

Sin embargo, al realizar algunas pruebas experimentales para confirmar su correcto funcionamiento, se puede observar que
la velocidad del algoritmo es considerablemente lenta, especialmente con las instancias más grandes. Este cuello de botella
se produce por la función \texttt{get\_weight()} de tsplib95, que realiza varias comprobaciones al llamarse. Más allá de la
implementación del algoritmo en sí, se puede agilizar la ejecución realizando un precálculo de la matriz de distancias a un
\textit{array} de \texttt{NumPy}. De este modo, las consultas pasan a ser accesos a memoria extremadamente rápidos.

La matriz de distancias se puede obtener de la siguiente manera:
\newline
\begin{lstlisting}[style=PythonStyle]
import tsplib95
import numpy as np

def extract_distance_matrix(problem):

  # Obtener la lista de nodos:
  nodes = list(problem.get_nodes())

  # Obtener la longitud de la lista (número de nodos):
  num_nodes = len(nodes)
  
  # Mapear los índices a IDs para evitar errores fuera de rango:
  node_to_idx = {node: i for i, node in enumerate(nodes)}
  
  # Inicializar una matriz vacía:
  matrix = np.zeros((num_nodes, num_nodes), dtype=np.float64)
  
  # Rellenar la matriz con los pesos o distancias:
  for i, u in enumerate(nodes):
    for j, v in enumerate(nodes):
      matrix[i, j] = problem.get_weight(u, v)
          
  # Devolver la matriz, los nodos y el mapeo:
  return matrix, nodes, node_to_idx
\end{lstlisting}

Al contar con la matriz de distancias precalculadas, se acelera el cálculo del coste de la ruta:
\newline
\begin{lstlisting}[style=PythonStyle]
def route_distance(route, distance_matrix):
  # Crear los pares de nodos consecutivos, incluyendo la vuelta al inicio:
  origins = route
  destinations = np.roll(route, -1)
  
  # Sumar todas las distancias en una misma operación de NumPy:
  return float(np.sum(distance_matrix[origins, destinations]))
\end{lstlisting}

El cálculo del \textit{fitness} es idéntico, aunque se debe adaptar la llamada a \texttt{route\_distance()} sustituyendo
el parámetro \texttt{problem} por la matriz de distancias:
\newline
\begin{lstlisting}[style=PythonStyle]
def fitness(route, dist_matrix):
  return 1.0 / route_distance(route, dist_matrix)
\end{lstlisting}

Por último, en la selección por torneo también se debe susituir este parámetro.

Una vez realizada esta serie de cambios para precalcular distancias, queda completa la implementación del algoritmo genético.

\subsection{Optimización por colonia de hormigas}
\label{subsec:aco_imp}

Para realizar la implementación del algoritmo de colonia de hormigas, se va a replicar el mismo esquema teórico descrito en la 
sección~\ref{sec:aco}. Se va a reutilizar la función \texttt{extract\_distance\_matrix()}, ya que ACO también necesita consultar
repetidamente las distancias entre las ciudades del problema.

Una diferencia respecto a GA es que, en ACO, cada hormiga construye su ruta directamente sobre los índices de la matriz de 
distancias. Por tanto, se puede reutilizar la función \texttt{route\_distance()} sin necesidad de modificarla. Únicamente es 
necesario traducir los índices a los identificadores reales de las ciudades en el momento de mostrar la solución final.

El primer elemento es la información heurística $\eta_{ij}$, definida como la inversa de la distancia entre ciudades:
\newline
\begin{lstlisting}[style=PythonStyle]
def compute_heuristic_matrix(distance_matrix):
 
  # Calcular la inversa de cada distancia, ignorando el aviso de división por
  # cero en la diagonal:
  with np.errstate(divide='ignore'):
    heuristic = 1.0 / distance_matrix
 
  # Anular la diagonal, ya que una ciudad no tiene conexión consigo misma:
  np.fill_diagonal(heuristic, 0.0)
 
  # Devolver la matriz de información heurística:
  return heuristic
\end{lstlisting}

El siguiente elemento a implementar es la feromona $\tau_{ij}$. El valor inicial debe ser igual para todas las rutas, para
evitar que ninguna parta con ventaja sobre el resto:
\newline
\begin{lstlisting}[style=PythonStyle]
def initialise_pheromone(num_nodes, init_val=1.0):
 
  # Crear una matriz cuadrada con el valor inicial:
  pheromone = np.full((num_nodes, num_nodes), init_val, dtype=np.float64)
 
  # Anular la diagonal, ya que una ciudad no tiene conexión consigo misma
  np.fill_diagonal(pheromone, 0.0)
 
  # Devolver la matriz de feromona inicializada:
  return pheromone
\end{lstlisting}

Con la información heurística y la feromona, se puede realizar la construcción de la ruta por parte de una única hormiga.
Dicha hormiga selecciona la siguiente ciudad de entre las que todavía no han sido visitadas, mediante el mecanismo estocástico
definido por la expresión $\tau_{ij}^{\alpha}\eta_{ij}^{\beta}$:
\newline
\begin{lstlisting}[style=PythonStyle]
import random
 
def build_ant_route(pheromone, heuristic, alpha, beta, num_nodes):
 
  # Seleccionar una ciudad inicial aleatoria:
  start = random.randrange(num_nodes)
  route = [start]
  visited = {start}
  current = start
 
  # Repetir hasta visitar todas las ciudades:
  while len(route) < num_nodes:
 
    # Obtener las ciudades que todavía no se han visitado:
    candidates = [c for c in range(num_nodes) if c not in visited]
 
    # Calcular el peso de cada conexión candidata:
    weights = [
        (pheromone[current, c] ** alpha) * (heuristic[current, c] ** beta)
        for c in candidates
    ]
 
    # Seleccionar la siguiente ciudad de forma probabilística:
    next_city = random.choices(candidates, weights=weights, k=1)[0]
 
    # Anadir la ciudad seleccionada a la ruta:
    route.append(next_city)
    visited.add(next_city)
    current = next_city
 
  # Devolver la ruta completa como índices de la matriz de distancias:
  return route
\end{lstlisting}

La función \texttt{random.choices()} implementa el mecanismo de $p_{ij}^{k}$, ya que la probabilidad de cada ciudad 
candidata es proporcional a su peso frente a la suma de los pesos de todos los candidatos. 

Se puede plantear un pequeño ejemplo con valores artificiales de feromona. Suponiendo el siguiente ejemplo, donde $\tau$
es el valor de feromona, $d$ la distancia de la ciudad candidata a la actual, y $\eta$ la información heurística:
\begin{verbatim}

  candidato 13 (idx=12): tau=0.600, d=975.0, eta=0.00103
  candidato 31 (idx=30): tau=1.000, d=146.0, eta=0.00685
\end{verbatim}

Utilizando los parámetros $\alpha = 1 $ y $\beta = 3$, las probabilidades resultantes quedan:
\begin{verbatim}
  p(1 -> 6)  = 0.1709
  p(1 -> 13) = 0.0017
  p(1 -> 31) = 0.8274
\end{verbatim}

Se puede observar lo siguiente: aunque la conexión a la ciudad 6 cuenta con el mayor valor de feromona, la ciudad 31 
recibe una probabilidad considerablemente mayor, debido a que su distancia es mucho menor. Esto ocurre porque la información
heurística está elevada al exponente $\beta = 3$, que amplifica notablemente las diferencias de distancia frente a las de 
feromona. Con esto se muestra la importancia del equilibro entre explotación de la información heurística y explotación de la
feromona.

Aplicando la función de construcción de rutas sobre \texttt{berlin52}, con una inicialización de feromona uniforme, se obtiene:

Como todavía no existe información de feromona, la ruta obtenida depende principalmente de la información heurística, es
decir, de las distancias entre ciudades. No obstante, cada ejecución aislada de esta prueba devolvuelve una ruta diferente,
ya que la ciudad inicial se selecciona aleatoriamente.

Una vez que una única hormiga es capaz de construir una ruta completa, se puede reproducir el proceso para toda la colonia:
\newline

def build_colony_routes(pheromone, heuristic, alpha, beta, num_nodes, num_ants):
 
  # Construir una ruta por cada hormiga de la colonia:
  return [
      build_ant_route(pheromone, heuristic, alpha, beta, num_nodes)
      for _ in range(num_ants)
  ]
\end{lstlisting}

Para evaluar las rutas obtenidas, se puede reutilizar directamente la función \texttt(route\_distance()). Tomando un 
pequeño ejemplo con una colonia de cinco hormigas, las rutas iniciales devuelven las siguientes distancias:
\begin{verbatim}
  >>> num_nodes = len(list(problem.get_nodes()))
  >>> dm, _, _ = extract_distance_matrix(problem)
  >>> hm = compute_heuristic_matrix(dm)
  >>> pm = initialise_pheromone(num_nodes, init_val=1.0)
  >>> routes = build_colony_routes(pm, hm, alpha=1.0, beta=3.0,

  >>> distances = [route_distance(r, dm) for r in routes]
  >>> print([f"{d:.2f}" for d in distances])
  ['13576.00', '10690.00', '11210.00', '15073.00', '11720.00']
\end{verbatim}

Después de construir y evaluar las rutas de todas las hormigas en una iteración, se debe actualizar la matriz de 
feromona. Esta actualización combina la evaporación de la feromona existente con el depósito realizado por la hormiga,
en proporción a la calidad de su ruta:
\newline
\begin{lstlisting}[style=PythonStyle]
def update_pheromone(pheromone, routes, distances, rho, Q):
 
  # Aplicar la evaporación a toda la matriz de feromona:
  pheromone *= (1 - rho)
 
  # Recorrer cada hormiga junto con la longitud de su ruta:
  for route, length in zip(routes, distances):
 
    # Calcular la cantidad de feromona a depositar:
    deposit = Q / length
 
    # Depositar feromona sobre cada conexión utilizada por la ruta:
    for i in range(len(route)):
      a, b = route[i], route[(i + 1) % len(route)]
      pheromone[a, b] += deposit
      pheromone[b, a] += deposit
 
  # Devolver la matriz de feromona actualizada:
  return pheromone
\end{lstlisting}

Es importante destacar que el depósito se realiza en ambos sentidos de la conexión, ya que se está trabajando con el TSP
simétrico. El término \texttt{Q / length} implementa directamente la expresión $\Delta\tau_{ij}^{k} = Q/L_k$, sumando dicha
cantidad únicamente sobre las conexiones efectivamente utilizadas por cada hormiga.

Una vez implementados todos los elementos anteriores, se puede construir el algoritmo de colonia de hormigas al completo de 
la siguiente manera:
\newline
\begin{lstlisting}[style=PythonStyle]
def ant_colony_algorithm(
  distance_matrix,
  num_ants,
  num_iterations,
  alpha,
  beta,
  rho,
  Q):
 
  # Obtener el numero de ciudades del problema:
  num_nodes = distance_matrix.shape[0]
 
  # Calcular la informacion heurística:
  heuristic_matrix = compute_heuristic_matrix(distance_matrix)

  # Inicializar la feromona:
  pheromone_matrix = initialise_pheromone(num_nodes)
 
  # Inicializar la variable para la mejor ruta encontrada:
  best_global_solution = None
 
  # Inicializar la mejor distancia (infinito para garantizar su actualización):
  best_global_distance = float('inf')
 
  # Iterar por cada iteración del algoritmo:
  for iteration in range(num_iterations):
 
    # Construir las rutas de todas las hormigas de la colonia:
    routes = [
        build_ant_route(pheromone_matrix, heuristic_matrix, alpha, beta, num_nodes)
        for _ in range(num_ants)
    ]
 
    # Evaluar la longitud de cada ruta construida:
    distances = [route_distance(route, distance_matrix) for route in routes]
 
    # Determinar la mejor hormiga de la iteración actual:
    best_iteration_idx = int(np.argmin(distances))
 
    # Si la mejor hormiga de la iteración mejora la solución global:
    if distances[best_iteration_idx] < best_global_distance:
 
      # Actualizar la distancia global:
      best_global_distance = distances[best_iteration_idx]
 
      # Guardar una copia de la solución:
      best_global_solution = routes[best_iteration_idx].copy()
 
    # Actualizar los niveles de feromona mediante evaporación y depósito:
    pheromone_matrix = update_pheromone(
        pheromone_matrix, routes, distances, rho, Q
    )
 
    # Se imprime la metrica de convergencia alcanzada en la iteración actual:
    print(
      f"Iteración {iteration + 1} | "
      f"Mejor distancia: {best_global_distance:.2f}"
    )
 
  # Devolver la mejor ruta y su distancia:
  return best_global_solution, best_global_distance
\end{lstlisting}

\subsection{Recocido simulado}
\label{subsec:sa_imp}

Para realizar la implementación del algoritmo de recocido simulado, se va a replicar el mismo esquema teórico descrito en la 
sección~\ref{sec:sa}. De nuevo, se van a reutilizar algunas funciones descritas anteriormente, como 
\texttt{extract\_distance\_matrix()} o \texttt{route\_distance()}. 

Para generar la solución inicial, se puede reutilizar directamente la función \texttt{generate\_individual()} del algoritmo 
genético, pasando la lista de índices como argumento:
\newline
\begin{lstlisting}[style=PythonStyle]
  solution = create_individual(list(range(num_nodes)))
\end{lstlisting}

A continuación, se debe implementar el operador de generación de soluciones vecinas. Como se comentaba en la 
sección~\ref{subsec:sa_neighbour_sol_gen}, se emplea \textit{Inversion}. A diferencia del operador de mutación de AG, esta
operación no depende de ninguna probabilidad, ya que en cada iteración se genera siempre una única solución vecina:
\newline
\begin{lstlisting}[style=PythonStyle]
import random

def generate_neighbour(solution):

  # Realizar una copia de la solución actual:
  neighbour = solution.copy()

  # Determinar la longitud de la solución:
  size = len(neighbour)

  # Seleccionar y ordenar dos puntos de corte aleatorios:
  point1, point2 = sorted(random.sample(range(size), 2))

  # Invertir el segmento comprendido entre ambos puntos:
  neighbour[point1:point2+1] = reversed(neighbour[point1:point2+1])

  # Devolver la solución vecina:
  return neighbour
\end{lstlisting}

Aplicando esta función sobre una solución inicial cualquiera de \texttt{berlin52}, se obtiene:
\begin{verbatim}
  >>> num_nodes = len(list(problem.get_nodes()))
  >>> dm, _, _ = extract_distance_matrix(problem)
  >>> sol = create_individual(list(range(num_nodes)))
  >>> print(route_distance(sol, dm))
  28867.0
  >>> neigh = generate_neighbour(sol)
  >>> print(route_distance(neigh, dm))
  28421.0
\end{verbatim}

En este caso concreto, la solución vecina obtiene un coste menor que la solución original, por lo que sería aceptada de forma
directa según la regla de aceptación $\Delta E = 28421 - 28867 = -446 \leq 0$. 

Sin embargo, la solución vecina no siempre mejora a la actual. Cuando $\Delta E > 0$, la aceptación de la solución pasa a 
depender de una probabilidad determinada por la temperatura actual, según la función de Boltzman: $P(aceptar) = e^{-\Delta 
E/T}$. Para ver la inflluencia de la temperatura en esta probabilidad, se puede tomar un mismo valor de $\Delta E$, por 
ejemplo $\Delta E = 50$, y comparar el resultado con dos temperaturas muy distintas:

\begin{verbatim}
  T = 100  ->  P(aceptar) = e^(-50/100) = e^(-0.5) = 0.6065
  T = 1    ->  P(aceptar) = e^(-50/1)   = e^(-50)  = 1.93e-22
\end{verbatim}

Se puede observar que, para una temperatura elevada, la probabilidad de aceptar una solución con el mismo valor de $\Delta E$
es relativamente alta, en torno al $60\%$. Sin embargo, cuando la temperatura se ha enfriado hasta $T=1$, la probabilidad se
vuelve prácticamente nula. Esto confirma el comportamiento esperado: al principio de la ejecución, con temperaturas altas, el 
algoritmo acepta soluciones peores con mayor facilidad, mientras que, a medida que se la temperatura desciende, se vuelve 
más restrictivo.

El esquema de enfriamento elegido es el exponencial o geométrico. Su implementación es directa, ya que únicamente consiste en
multiplicar la temperatura actual por el factor $\alpha$ en cada iteración:
\newline
\begin{lstlisting}[style=PythonStyle]
  temperature *= alpha
\end{lstlisting}

Con todos los elementos anteriores, se puede construir el algoritmo de recocido simulado al completo de la siguiente manera:
\newline
\begin{lstlisting}[style=PythonStyle]
def simulated_annealing(distance_matrix, initial_temp, final_temp, alpha):

  # Obtener el numero de ciudades del problema:
  num_nodes = distance_matrix.shape[0]

  # Generar la solución inicial:
  current_solution = create_individual(list(range(num_nodes)))

  # Evaluar su coste:
  current_distance = route_distance(current_solution, distance_matrix)

  # Inicializar la mejor solución encontrada con la solución inicial:
  best_solution = current_solution.copy()
  best_distance = current_distance

  # Inicializar la temperatura al valor inicial:
  temperature = initial_temp
  iteration = 0

  # Repetir mientras la temperatura no alcance el valor final:
  while temperature > final_temp:

    # Generar una solución vecina mediante inversión:
    neighbour_solution = generate_neighbour(current_solution)
    neighbour_distance = route_distance(neighbour_solution, distance_matrix)

    # Calcular la diferencia de coste entre la vecina y la actual:
    delta_e = neighbour_distance - current_distance

    # Si la solución vecina mejora o iguala a la actual:
    if delta_e <= 0:

      # Se acepta directamente:
      current_solution = neighbour_solution
      current_distance = neighbour_distance

    # Si la solucion vecina es peor:
    else:

      # Se acepta con una probabilidad dependiente de la temperatura:
      acceptance_probability = math.exp(-delta_e / temperature)
      if random.random() < acceptance_probability:
        current_solution = neighbour_solution
        current_distance = neighbour_distance

    # Actualizar la mejor solución encontrada:
    if current_distance < best_distance:
      best_solution = current_solution.copy()
      best_distance = current_distance

    # Reducir la temperatura mediante el esquema de enfriamiento exponencial:
    temperature *= alpha

    iteration += 1

    # Se imprime la métrica de convergencia alcanzada en la iteración actual:
    print(
      f"Iteración {iteration} | Temperatura: {temperature:.2f} | "
      f"Mejor distancia: {best_distance:.2f}"
    )

  # Devolver la mejor ruta y su distancia:
  return best_solution, best_distance
\end{lstlisting}

\subsection{Búsqueda tabú}
\label{subsec:ts_imp}

Para realizar la implementación del algoritmo de búsqueda tabú, se va a replicar el mismo esquema teórico descrito en la 
sección~\ref{sec:ts}. La solución se representa igual que en las metaheurísticas anteriores, mediante índices de la matriz
de distancias, por lo que se pueden reutilizar directamente funciones como \texttt{extract\_distance\_matrix()}, 
\texttt{route\_distance()} y \texttt{create\_individual()} para generar la solución inicial.

A diferencia del recocido simulado, donde se genera una única solución vecina en cada iteración, la búsqueda tabú 
necesita evaluar el vecindario de la solución actual al completo, para seleccionar la mejor alternativa posible. Teniendo
en cuenta que el operador de vecindad es \textit{Inversion} (\textit{2-opt}), se implementa de la siguiente forma:
\newline
\begin{lstlisting}[style=PythonStyle]
def generate_neighbourhood(solution):

  # Determinar la longitud de la solución:
  size = len(solution)
  neighbourhood = []

  # Recorrer todos los pares de puntos de corte posibles:
  for i in range(size - 1):
    for j in range(i + 1, size):

      # Generar la solución vecina invirtiendo el segmento [i, j]:
      neighbour = solution.copy()
      neighbour[i:j+1] = reversed(neighbour[i:j+1])

      # Identificar el movimiento mediante las dos ciudades del corte:
      move = frozenset((solution[i], solution[j]))

      neighbourhood.append((neighbour, move))

  # Devolver la lista de pares (solución vecina, movimiento):
  return neighbourhood
\end{lstlisting}

Cada movimiento se identifica mediante \texttt{frozenset} con las dos ciudades situadas en los puntos de corte, en lugar
de las posiciones $i$ y $j$. De este modo, si más adelante estas mismas dos ciudades vuelven a aparecer como extremos de 
un corte, aunque estén en posiciones distintas de la ruta, el movimiento se reconoce como el mismo a efectos de la lista 
tabú. El uso de \texttt{frozenset} también permite que el orden de las ciudades no importe: $(a, b)$ y $(b, a)$ se tratan 
como el mismo movimiento.

Aplicando esta función sobre una solución de \texttt{berlin52}, se obtiene un vecindario de tamaño:

\begin{verbatim}
  >>> sol = create_individual(list(range(num_nodes)))
  >>> neigh = generate_neighbourhood(sol)
  >>> print(len(neigh))
  1326
\end{verbatim}

El resultado se corresponde con $\binom{52}{2} = 1326$, el número de pares de puntos de corte posibles para una ruta de 
52 ciudades.

Una vez generado el vecindario, la búsqueda tabú tiene que evaluar cada solución candidata y seleccionar la mejor 
alternativa posible, pero respetando la lista tabú y el criterio de aspiración. Para implementar la lista tabú, se utiliza 
un diccionario que asocia cada movimiento con la iteración en la que deja de estar restringido. Con esta estructura, se 
evita recorrer y decrementar manualmente un contador en cada movimiento almacenado, ya que simplemente se puede comparar la 
iteración actual con el valor almacenado:
\newline
\begin{lstlisting}[style=PythonStyle]
  is_tabu = tabu_list.get(move, -1) > iteration
\end{lstlisting}

Si el movimiento no está en el diccionario, \texttt{tabu\_list.get(move, -1)} devuelve $-1$, por lo que la comparación
resulta falsa y el movimiento se considera libre.

Sin embargo, un movimiento restringido puede aceptarse igualmente si la solución que genera mejora la mejor solución
encontrada hasta el momento. Este criterio de aspiración se comprueba de la siguiente manera:
\newline
\begin{lstlisting}[style=PythonStyle]
  aspirant = neighbour_distance < best_distance
\end{lstlisting} 

De este modo, un movimiento solo se descarta como candidato cuando está restringido y, además, no cumple el criterio de 
aspiración:
\newline
\begin{lstlisting}[style=PythonStyle]
  if is_tabu and not aspirant:
    continue
\end{lstlisting}

Para comprender el funcionamiento de este criterio, se puede considerar el siguiente ejemplo. Suponiendo que en la 
iteración 3 se aplica un movimiento sobre las ciudades $(12, 47)$, con un valor de \textit{tabu tenure} de $10$, por lo que
este movimiento se restringe hasta la iteración 13:
\begin{verbatim}
  tabu_list[frozenset((12, 47))] = 13
\end{verbatim}
Si en la iteración 8, este mismo movimiento vuelve a generar una solución con un coste de 7600, y la mejor solución 
global encontrada hasta el momento tiene un valor de 7620, el movimiento se admite igualmente, a pesar de seguir
restringido ($8 < 13$), ya que $7600 < 7620$ cumple el criterio de aspiración.

Por último, una vez seleccionado el movimiento a aplicar entre los candidatos admisibles, se añade a la lista tabú, y se
mantiene restringido durante las próximas \textit{tabu tenure} iteraciones:
\newline
\begin{lstlisting}[style=PythonStyle]
  tabu_list[best_candidate_move] = iteration + tabu_tenure
\end{lstlisting}

Con todos los elementos anteriores, se puede construir el algoritmo de búsqueda tabú al completo de la siguiente manera:
\newline
\begin{lstlisting}[style=PythonStyle]
def tabu_search(distance_matrix, num_iterations, tabu_tenure):

  # Obtener el número de ciudades del problema:
  num_nodes = distance_matrix.shape[0]

  # Generar la solución inicial:
  current_solution = create_individual(list(range(num_nodes)))

  # Evaluar su coste:
  current_distance = route_distance(current_solution, distance_matrix)

  # Inicializar la mejor solución encontrada con la solución inicial:
  best_solution = current_solution.copy()
  best_distance = current_distance

  # Inicializar la lista tabú como un diccionario vacío:
  tabu_list = {}

  # Iterar según el numero máximo de iteraciones establecido:
  for iteration in range(num_iterations):

    # Generar el vecindario completo de la solución actual:
    neighbourhood = generate_neighbourhood(current_solution)

    best_candidate = None
    best_candidate_distance = float('inf')
    best_candidate_move = None

    # Evaluar cada solución vecina del vecindario:
    for neighbour, move in neighbourhood:
      neighbour_distance = route_distance(neighbour, distance_matrix)

      # Comprobar si el movimiento está actualmente restringido:
      is_tabu = tabu_list.get(move, -1) > iteration

      # Criterio de aspiración -> se admite un movimiento tabu si mejora la
      # mejor solucion encontrada hasta el momento:
      aspirant = neighbour_distance < best_distance

      # Si el movimiento está restringido y no cumple el criterio de aspiración,
      # se descarta como candidato:
      if is_tabu and not aspirant:
        continue

      # Actualizar el mejor candidato admisible encontrado hasta el momento:
      if neighbour_distance < best_candidate_distance:
        best_candidate = neighbour
        best_candidate_distance = neighbour_distance
        best_candidate_move = move

    # Adoptar el mejor candidato admisible como nueva solución actual:
    current_solution = best_candidate
    current_distance = best_candidate_distance

    # Restringir el movimiento aplicado durante tabu_tenure iteraciones:
    tabu_list[best_candidate_move] = iteration + tabu_tenure

    # Actualizar la mejor solución encontrada, si corresponde:
    if current_distance < best_distance:
      best_solution = current_solution.copy()
      best_distance = current_distance

    # Se imprime la métrica de convergencia alcanzada en la iteración actual:
    print(f"Iteración {iteration + 1} | Mejor distancia: {best_distance:.2f}")

  # Devolver la mejor ruta y su distancia:
  return best_solution, best_distance
\end{lstlisting}

\section{Hiperparámetros}
\label{sec:hyperparams}

La decisión sobre qué hiperparámetros utilizar para cada metaheurística es, sin duda, la decisión más crítica de todo el
proyecto. Una pequeña variación en estos valores puede cambiar notablemente el resultado obtenido, por lo que es 
necesario realizar una justificación sobre los valores seleccionados, y no hacerlo de manera arbitraria.

Una opción sencilla sería ajustar los hiperparámetros de cada algoritmo específicamente para cada una de las instancias,
buscando el mejor rendimiento posible en cada caso. Sin embargo, este enfoque no sería adecuado para el propósito del trabajo: 
si los parámetros se afinan expresamente para acercarse al óptimo de cada instancia concreta, se estaría realizando una especie
de metaingeniería sobre el propio experimento, lo que dificultaría la comparación justa entre algoritmos. 

En su lugar, se ha optado por adoptar los valores de referencia empleados en estudios similares de la literatura, de forma que
la elección de parámetros esté respaldada por trabajos ya contrastados, y no por una búsqueda de optimización particular para
este trabajo. En concreto, el estudio elegido ha sido \cite{halim2019}, debido a varias razones. Para empezar, el estudio que
plantean los autores es muy similar al de este trabajo, ya que evalúan diferentes heurísticas y metaheurísticas aplicadas al 
Problema del Viajante simétrico. Adicionalmente, los autores utilizan las cuatro metaheurísticas descritas en el presente
trabajo: algoritmos genéticos, colonia de hormigas, recocido simulado y búsqueda tabú, de modo que no es necesario recurrir 
a múltiples fuentes, lo cual dificultaría la comparación entre los futuros resultados obtenidos frente a los que proporcionan
las fuentes. 

El último de los motivos, y el más importante, es que los autores proporcionan los hiperparámetros utilizados en el estudio 
de forma explícita. Por tanto, es posible trasladar dichos valores a este trabajo, para posteriormente realizar una comparación
entre los resultados obtenidos con los que se muestran en el artículo de referencia.

Sin embargo, no todos los hiperpárametros y configuraciones son trasladables directamente a este estudio. Se tiene que tener en
cuenta lo siguiente:
\begin{itemize}
  \item En el algoritmo genético, no se proporcionan las probabilidades de cruce y mutación, así como el número de individuos
  a seleccionar mediante elitismo. Además, los operadores empleados son diferentes: la mutación combina tres de los operadores
  descritos en la sección~\ref{subsec:mutation}, y la selección se realiza por ruleta. Se tendrá que tener en cuenta esta 
  serie de factores a la hora de realizar la comparación de esta metaheurística.
  \item En el recocido simulado, se utiliza un valor de $T=0.025$ sorprendentemente bajo. En esta escala, el algoritmo no 
  aceptaría una solución peor en prácticamente ninguna situación, anulando por completo el propósito de esta metaheurística.
  Asimismo, tampoco se menciona el valor de temperatura final. Se deben buscar unos valor de $T_{inicial}$ y $T_{final}$ 
  adecuados.
  \item En la búsqueda tabú, se asume que el término \textit{action list} es el equivalente a \textit{tabu tenure}.
\end{itemize}

Un detalle a destacar es que el parámetro de número de iteraciones en el recocido simulado es innecesario, puesto que el 
algoritmo termina cuando se alcanza la temperatura final.

Para solventar estas cuestiones, se ha decidido lo siguiente:
\begin{itemize}
  \item Para los valores de probabilidad de cruce y mutación, se van a utilizar los descritos en \cite{razali2011}:
  \begin{itemize}
    \item Probabilidad de cruce: $60\%$.
    \item Probabilidad de mutación: $10\%$.
  \end{itemize}
  \item Para los valores de temperatura inicial y final, se van a utilizar los descritos en \cite{ye2013}:
  \item Temperatura inicial: $10.000$.
  \item Temperatura final: $0.1$.
\end{itemize}

Existen otros tres parámetros que no se mencionan en esta parte de la fuente, pero sí se han incluido en la implementación de
los algoritmos. Por tanto, requieren un valor y su debida justificación:
\begin{itemize}
  \item En el algoritmo genético, se debe proporcionar un valor para \texttt{num\_elites}, esto es, los elementos a elegir por
  elitismo. Se adopta un valor de \texttt{num\_elites = 1}, siguiendo la estrategia elitista simple descrita en 
  \cite{abdoun2012}, en la que únicamente el mejor cromosoma de la población se preserva para la siguiente generación.
  \item También en el algoritmo genético, específicamente en el operador de selección por torneo, se debe dar un valor a 
  \texttt{k}, que determina el número de individuos que participan en el torneo. En \cite{razali2011} se indica que, 
  habitualmente, se aplica un torneo binario, por lo que se va a seleccionar un valor de \texttt{k = 2}.
  \item En colonia de hormigas, es necesario dar un valor a la constante \texttt{Q}, encargada de dividirse por la longitud de
  la ruta para obtener la cantidad de feromona depositada por la hormiga. Sin embargo, la cuestión con esta variable es que 
  \texttt{Q} depende de la escala de la instancia, y no es posible determinar un valor ``genérico'' para el experimento. Por 
  tanto, se va a establecer un valor de \texttt{Q = 100}, el cual ha sido validado empíricamente sobre \texttt{berlin52}
  durante la fase de implementación.
\end{itemize}

\section{Criterio de parada adicional}
\label{sec:stop_crit}

Una vez establecidos los hiperparámetros para las cuatro metaheurísticas, únicamente quedaría ejecutar el experimento. No 
obstante, durante una serie de pruebas finales para comprobar la correcta implementación de los algoritmos, se vio claramente
como el número de iteraciones o generaciones seleccionado en el artículo es excesivamente alto. Los propios autores señalan las
limitaciones que presentan estas configuraciones, especialmente con la búsqueda tabú, cuya ejecución más larga duró unas 19 
horas aproximadamente.

Adicionalmente, se pudo comprobar de forma empírica que la necesidad de un número de iteraciones es prácticamente nula, ya que
los algoritmos convergen, generalmente, bastante rápido, de modo que alcanzan el óptimo, o un valor próximo a él, sin la 
necesidad de alcanzar el número de iteraciones máximo establecido. Por tanto, y para evitar una ejecución eterna para cada una
de las instancias, se va a introducir un criterio de parada adicional, basado en el estancamiento de los algoritmos. Su 
funcionamiento es ciertamente sencillo: si se cumple una determinada cantidad de iteraciones sin obtener ninguna mejora del
resultado, el algoritmo finaliza.

Sin embargo, surge ahora el problema de determinar el número de iteraciones sin mejora que señalan un estancamiento del
algoritmo. Existen dos posibilidades para ello:
\begin{itemize}
  \item Seleccionar un valor \textbf{fijo}, por ejemplo: 150 iteraciones.
  \item Seleccionar un valor \textbf{proporcional al número de iteraciones}, por ejemplo: $\textit{num\_iter} / 10$ iteraciones.
\end{itemize}

Para simplificar esta decisión, y teniendo en cuenta la relativa velocidad de convergencia de las metaheurísticas observada en
las diferentes pruebas con \texttt{berlin52}, se ha decidido lo siguiente: los algoritmos finalizarán su ejecución si no se
consigue mejorar la mejor solución encontrada en \textbf{200 iteraciones}. Se cree que es un valor lo suficientemente permisivo
como para permitir la posibilidad de mejorar progresivamente a lo largo de la ejecución, y a la vez se limita la posibilidad de 
que un algoritmo permanezca estancado durante demasiado tiempo, añadiendo tiempo de ejecución ``muerto'' a la estadística final.

En la implementación, este valor de estancamiento se ha denominado \texttt{patience}, y se introduce como un argumento más a 
cada uno de los algoritmos. El criterio de parada se implementa de la siguiente manera: en primer lugar, se inicializa a cero un
contador de iteraciones estancadas.

\begin{verbatim}
  stagnant_iterations = 0
\end{verbatim}

Al evaluar la mejor distancia de la evaluación, si mejora a la anterior, se reinicia el contador a cero:

\begin{verbatim}
  if current_distance < best_distance:
    best_solution = current_solution.copy()
    best_distance = current_distance
    stagnant_iterations = 0
\end{verbatim}

En caso contrario, se incrementa el contador en la unidad:

\begin{verbatim}
  else:
    stagnant_iterations += 1
\end{verbatim}

Al final de la iteración, y después de imprimir la métrica de convergencia, se compara el contador con el valor 
\texttt{patience}. Si lo ha alcanzado, finaliza el bucle:

\begin{verbatim}
  if stagnant_iterations >= patience:   
    break
\end{verbatim}
